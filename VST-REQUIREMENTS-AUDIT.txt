2. 第七轮（04cde28）发现并修复的流程遗漏

A. 删除最后一个插件后，播放按钮可能永久处于 pausing。
原因：两个宿主切换 watcher 都更新 requestId，迟到的原生暂停响应被当作过期响应丢弃。
修复：离开原生图时保留暂停请求的身份，等待其结算后再允许 Web Audio 播放。
回归覆盖实际播放组合层与 playback store，而非仅检查独立 native adapter。

B. 导出准备期间修改插件、Undo 或重新定位，可能混合旧混音与新插件状态。
原因：导出先复制项目，再等待捕获，之后仅按 slot ID 向旧副本拷入新 state。
修复：状态捕获后一次性冻结原项目的完整状态；切换项目不混入新项目，取消不启动渲染。
冻结语义为“捕获完成时”，并重新校验格式和内置效果限制。后续渲染和编码固定使用该快照。

C. 第三方插件向 stdout 打印诊断文本，会破坏扫描和宿主 JSON 协议。
修复：helper 启动时保存原 stdout 的私有、不可继承输出通道，再重定向插件可见的
OS stdout 与 C runtime fd 1 到空设备；仅宿主 JSON 使用私有通道，stderr 保持原有行为。
普通 Tauri 启动不重定向。不会靠跳过非 JSON 行掩盖问题，也不接受插件伪造的 JSON 行。
原生夹具分别通过 C puts、Rust stdout、Win32 WriteFile 输出噪声和 JSON 形文本：
旧协议测试失败；修复后扫描仅返回一个 JSON 对象，宿主返回四条正确请求响应。

D. VST2/VST3 修改混响或延迟参数后，导出可能沿用加载时的尾音长度。
修复：在停止处理的导出准备阶段刷新当前参数、latency 和 tail；启动探测后再刷新并
计算导出长度。保留同一插件实例、PDC 和 30 秒截断提示，实时处理不增加尾音属性轮询。
夹具覆盖首次处理后才报告尾音、仅尾音变化而延迟不变、无限尾音截断。

10. 第十二轮：离线导出的插件处理模式（起点 ce76f77）

发现：Tauri 导出 helper 已发送 offline=true，但 native load 忽略该标志，VST3 的
setupProcessing/ProcessData 和 VST2 process level 固定实时；AU 未通知 OfflineRender。
因此有独立离线质量、延迟或尾音配置的插件可能使用错误的渲染路径。

现已接入：
  - load 接受严格 boolean；update 未指定时继承，模式变化才重建，status 返回模式。
  - VST3 setup 和全部音频/零帧参数块保持同一 mode。切换需要停止并重新 setup；
    从控制/UI 线程创建、设置离线图，未将 setupProcessing/总线协商移入 DSP worker。

    线程及嵌套上下文退出后恢复原值，不改变 state envelope 和 shell 子插件身份。
  - AUv2/AUv3 的 C 桥接单位在未初始化时设置可选属性 37，然后初始化原配置。
    缺失或只读时保留普通效果处理；真实 setter/query/init 错误不吞掉。
    回滚失败持久保留错误，后续同模式请求、切换和 prepare 都拒绝，必须重载实例。
    auol 专用离线效果需要 priming/preflight 生命周期，继续明确排除。

先 pause/snapshot，再于同一 UI 线程按相同采样率创建临时离线会话。成功、失败和退出
都在 UI 线程回收；原预览实例、控制器、模式、参数、循环及 monitor mask 保留。
离线会话拒绝声卡播放，更新为 offline 时保留位置/循环并暂停。

11. 第十三轮：VST3 时序查询和重新激活（起点 d7aa2f3）

上一轮标记的线程问题已修复。实时 process/flush、离线导出和 PDC 更新路径只消费原子
latency/tail 缓存，不再从音频工作线程调用这两个 SDK getter。新增 reader 独立于原生
编辑器和 edit controller，校验创建线程；实例释放前在同一生命周期锁下切断引用。

控制线程在 DSP 已停止时执行 setProcessing(false)、setActive(false/true)，再查询新值。
active/processing 状态与 worker 共用原子字段，避免出现两份生命周期状态。原生停止或
重新激活失败会使实例持续失效，之后 process/flush/prepare/模式切换均拒绝，要求重载。
getter 自身产生的新通知不会被末尾清零；同一暂停范围内最多再读一次，仍不稳定则失败。

实时恢复复用 SnapshotPause；离线探测由 worker 发送 Timing ticket，UI 查询后确认，
worker 才继续缓存/PDC。ticket 在进入 SDK 前检查绝对期限及取消状态；请求已过期且
worker 尚未来得及失效时也不会迟到执行。在途 SDK 查询则持互斥保护，worker 不能因为
超时或取消而与它并行处理。SDK 本身挂起仍由既有隔离进程终止机制解决。

审查发现并修复：
  - ticket 仅用 active 标志时，UI 可能在 deadline 后、worker 失效前抢先进入 SDK。
  - 直接离线会话导出时，AU 窗口关闭 idle 会等待 Barrier，而 worker 正等待 Timing。
    现在实际渲染会话延后 idle，Event::Render 完成后恢复；独立的原预览仍正常维护。
  - 多插件依次首次改变延迟会消耗原全图单次预算，被误判为不稳定。现按唯一 slot ID
    各允许一次启动重协商，重复变化继续明确失败；日志不再把内部哨兵当作实际新延迟。
